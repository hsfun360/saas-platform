## Purpose

Golf operations: courses, tee-time scheduling and booking, flights/pairings, front-desk registration and billing, handicap and guest control, group and tournament bookings; competitions, pro-shop and scoring as needed later.

## Domain model - how a golf course is set up

Golf courses are built from NINE-hole **unit courses** first.
A unit course has a type: `out` (front nine only), `in` (back nine only) or `composite` (either).
A full 18-hole **course** is then formed by picking two unit courses - the 1st as the OUT (front) nine and the 2nd as the IN (back) nine - plus optional standby and floodlit fallback nines.
Hole numbering follows the type (OUT -> 1-9, IN -> 10-18).

## Owns (data)

All 37 tables live in the `golf` Postgres schema; `companyId`, `memberId`, `membershipTypeId`, `courseId`-style peer references are plain UUIDs (no cross-service FK); intra-service parent-child links are real FKs.

- `golf.UnitCourse` - 9-hole unit course master file (code, type, completion minutes, floodlight + lighting-fee lead time).
  **Built.**
- `golf.UnitCourseHole` - hole rows of a unit course (par 3/4/5, handicap index, remarks); numbering fixed by the type (OUT 1-9, IN 10-18, COMPOSITE 1-18).
  HCP parity follows the numbering context: holes 1-9 take ODD indexes, holes 10-18 EVEN, so an OUT+IN pairing yields a full 1-18 set.
  Intra-service FK, cascades with the unit course.
  **Built.**
- `golf.UnitCourseTeeBox` + `golf.UnitCourseTeeBoxDistance` - tee boxes of a unit course (colour code, number, description, measurement unit meter/yard) with PER-HOLE distances (the scorecard's yardage rows; OUT/IN totals are computed, never stored).
  Cascade with the unit course.
  Difficulty ratings (course/slope) deliberately live at the 18-hole Course level (2.2.4), not here.
  **Built.**
- `golf.Course` - the 18-hole course (spec 2.2.4): code/display sequence/description, first nine (OUT|COMPOSITE), second nine (IN|COMPOSITE, must differ from first), optional alternate nine and night nine (must be a floodlit unit course), cross over time, course photo (GCS URL).

  **Built.**
- `golf.TransactionTypeRate` - the pricing of a transaction type: effective-dated price cards (unique per (type, effectiveDate); resolution = the ACTIVE card with the latest effective date on-or-before the play date, same rule as tee-time sets).

  Intra-service FK, cascades with the transaction type.

  BILLING RULES (recorded 2026-08-06, binding at the front desk): the green fee is charged AUTOMATICALLY at registration for every player EXCEPT a member whose Membership Type has `isGolfAllow` - so a valid member without golfing rights IS charged the green fee, at the MEMBER price; guests/visitors pay the visitor price.

  Manual amendment of a resolved price at billing is allowed only when the transaction type's `allowPriceOverride` is on.
- `golf.TransactionTypeElement` - the element lines of a PACKAGE transaction type (chargeType `package`, user decisions 2026-08-27), e.g. Weekday Twin Package 200.00 = 1 x share buggy (100.00) + 2 x caddy (50.00 each).
  Each line: `transactionTypeId` (the owning PACKAGE - parent column named to match `TransactionTypeRate`, user decision 2026-08-27; table renamed from the short-lived `TransactionTypePackageItem` via a guarded boot migration in app.js) + `elementTransactionTypeId` (a peer transaction type of the SAME company - never a package itself, no nesting; an element in use cannot become a package) + `quantity` (1-99) + `unitAmount` (the per-unit allocation of the package price - the revenue breakdown at billing) + `sortOrder`; unique (package, element).
  The package's own SELLING price stays in its flat `TransactionTypeRate` cards; the element sum is shown against it in the editor but deliberately NOT enforced.
  The package header additionally carries `autoTransactionTypeId` (required for packages; same-company, active, non-package - e.g. PAK1 -> GF1): the transaction type that receives the AUTOMATIC balance line at billing.
  Lines are replaced atomically inside the create/update transaction (`packageItems` in the POST/PUT payload); saving a package as a plain charge type clears its lines.
  Intra-service FK, cascades with the package.
  **Built.**
  PACKAGE BILLING RULES (user spec 2026-08-28, binding; supersedes the earlier per-element-tax decision):
  1. Selecting a package inserts DETAIL lines, not one line (analysis requirement): one line per element (quantity x the unit price stored on the element line, billed as-is) PLUS one automatic line to `autoTransactionTypeId` for the balance = package price minus the sum of the element lines.
     Example: PAK1 450.00 = BG1 1x101.00 + CD1 2x34.00 + GF1 auto 281.00.
  2. TAX: the PACKAGE's own tax scheme applies to EVERY generated line (the elements' schemes are ignored for package billing); the package Tax Scheme field is back on the setup form.
  3. ROUNDING: line taxes are computed per line, then the LAST generated line's tax is adjusted so the sum of line taxes equals the tax computed directly on the package amount (e.g. 5.72 + 3.85 + 15.91 = 25.48 -> adjust to force the direct 450.00 -> 25.47).

- `golf.GolfSetting` + `golf.AdvanceBookingOverride` - Golf Specification (per-company settings SINGLETON, pattern of membership.MembershipSetting / ar.Setting; user decisions 2026-09-17), maintained at `/golf/settings`.
  ADVANCE-BOOKING WINDOW: `advanceBookingDays` (0-365, general rule for everyone) + `advanceBookingHours` (0-23, early opening BEFORE midnight, club-wide, never overridable) + `allowMembershipTypeOverride`.
  Override lines (`membershipTypeId` value ref via membershipGateway, unique per company + type; PUT-replaced atomically; stored even while the flag is OFF, EFFECTIVE only while ON) grant privileged types an earlier window - most clubs use one number, so lines exist only where granted.

  `allowBookingMerge` (club-wide, default OFF; user decisions 2026-09-19) - the MERGE BOOKING rule for the booking stage.
  OFF = exclusive flights: the first confirmed booking claims the WHOLE flight regardless of player count; more players can only be added into that same booking (up to the slot's max players), never as a second booking.
  ON = shared flights: bookings attach to a flight until the slot's max players is reached (a 2-player booking leaves 2 seats open to another booking).
  The rule is read at booking time - flipping it never touches existing bookings.
  For an 18-hole booking it applies to BOTH occupied cells (start slot + crossover slot).
  `allowSameDayBooking` (default OFF; user decision 2026-09-21) - when OFF the booking window STARTS TOMORROW (club-local): today's flights are not bookable at all - golfers take today's flights by front-desk REGISTRATION (registration stage).
  ON = the window starts today.
  Lands in bookingWindow's dateFrom, so the Date picker minimum, search, lock and save all inherit it.
  Corner case: advance days 0 + same-day OFF = an empty window, a deliberate config outcome.
  `bookingLockMinutes` (1-60, default 5) - how long a clicked flight stays claimed while the player list is keyed.
  BOOKING LIMIT per day type (user decisions 2026-10-01, replacing the 2026-09-20 oneBookingPerDay boolean - a marker-guarded boot migration in app.js carried OFF over as 'none' and dropped the column): `bookingLimitWeekday` + `bookingLimitWeekend`, each 'none' | 'day' | 'session' (default 'day'; holidays = weekend via the calendar seam).

  `getGolfMemberStanding` returns `isJunior` + `principalMemberId`.

  CLOCKS: reserving flights on a tentative booking sets `holdExpiresAt` = now + `groupTentativeHoldHours` (0 = none; a held deposit keeps it off); Submit requires every planned day to have flights, computes the approval CONTEXT (bookingType, dayType, playDays, totalFlights/Seats, maxDaySharePct = the booking's cells against the course's grid, groupSharePct = ALL held groups on that course+date, startFormat, amount, catalogAmount, discountPct, manualPriceCount, perPlayerAmount, depositRequired, depositPct, organiserType, clubEvent) and starts the `golf-group-booking` workflow purpose through `workflowGateway.startWorkflow` (`entityRouteParam` makes the outcome bell open the booking page); no chain = approved at once.
  `applyApproval` snapshots `depositRequiredAmount` (the proforma's figure, else `groupDefaultDepositPct` of the bill total, 0 without a bill - written back to the bill so the proforma states it) and `depositDueAt` = the proforma's pay-by date if still ahead else today + `groupDepositDueDays`, at the club's END OF DAY (`endOfDayInZone`); held deposits >= required confirms at once.
  `recordDeposit` calls `refreshConfirmation` (approved -> booked when met).
  Rejection -> tentative with the flights RELEASED (`releaseFlights` drops flights without drawn players); recall (`workflowGateway.cancelForEntity`, the onCancelled handler) -> tentative with everything kept and the clock restarted; `reopen` (approved / booked / lapsed, refused once anyone is registered) -> tentative, resubmit required; `extendDeposit` ONCE per booking (body `{ depositDueDate, reason }`; stored as `depositDueExtendedAt` / `depositDueExtendedBy` / `depositDueExtensionReason`; the new date must be later than the current one).

  Handlers in `wiring/workflowHandlers.js` (`applyApproval` / `applyRejection` / `applyRecall`).

  SHARE CAPS + HOARDING CAP (lifecycle slice 2, 2026-10-11): `GolfSetting.groupShareCapWeekday` / `groupShareCapWeekend` (percent, 0 = none) are the HARD ceiling on what ALL live group bookings together may hold of a course's tee times on one day, whatever an approver decides; `groupMaxTentativePerUser` (0 = none) caps the TENTATIVE bookings with reserved flights one user holds.
  `BookingProfile.isClubEvent` (the club's own Monthly Medal / captain's day) is exempt from the caps and from the approval chain (Submit approves directly) and does not count as a "group"; only a caller who holds `/golf/settings` (`serviceContext.holdsMenu`) may set or clear it (meta ships `clubEventAllowed`).

  PIPELINE + WARNINGS (lifecycle slice 3, 2026-10-11): the worker scan warns ONCE per clock 24 hours ahead - a tentative booking's hold (`holdWarnedAt`) and an approved booking's deposit (`depositWarnedAt`; a deposit found met at warning time confirms instead) - and the markers clear whenever a clock restarts (flights re-reserved, recalled, reopened, extended, re-approved).

- `golf.BookingChange` - CHANGE BOOKING (user decisions 2026-10-14, approved structure).
  **Built.**
  An ordinary flight booking is amended without cancelling it: MOVE the flight (another course, date, tee time or holes - the desk locks the new flight exactly as when booking, with the booking's own seats and its own one-per-day evidence excluded via `excludeBookingId` on the availability and lock calls), change the ROSTER (add players up to the free seats, drop players; a line with `playerId` keeps that player, a line without one adds a player) or edit the HEADER (contact mobile, remarks).
  The booking number never changes; a registered player cannot be dropped and a booking with a registered player cannot be moved.
  `bookingChange.service.js` owns the flow: `plan` (the preview) and `apply` (the change, re-judged under the advisory locks of both dates) run every make-booking rule on the roster after the change (window, closures and slot roles when moved, capacity under the merge rule with the booking's own records excluded, minimum players, guest control and quota, handicap for the added players, the day or session limit, the junior rule), then cancel the dropped records (both nines), re-point the kept records (creating or destroying the crossover record when the holes change), create the added records, update the header, release the lock, raise any penalty, write the history row and queue ONE `golf.booking.changed` email to every affected player (dropped included).
  Cancellation-notice policy INSIDE the window (`noShowCharge.config` ON, judged against the ORIGINAL flight): a move to another flight on the SAME day is free; a move to ANOTHER day is a late cancellation of the original flight ('charge' raises the penalty for the booked players and moves the flight, 'refuse' blocks the move); dropped players are charged per player when the basis is 'player' and a partial drop charges nothing when the basis is 'booking'; 'refuse' blocks drops; outside the window every change is free (`policy()` in the service, unit-tested).
  The penalty is a `golf.NoShowCharge` row with reason 'late-cancel', waivable with a reason, posted to AR after commit like the cancel path.
  ONE `golf.BookingChange` row per amendment: bookingProfileId, bookingNo, `changeNo` (1, 2, 3 per booking), `changeType` move | roster | header | mixed (`booking.constants CHANGE_TYPES`), `before` / `after` JSONB (course, date, tee and cross time, holes, contact, remarks, player lines), `summary` (the sentence the desk confirmed), `reason`, `noShowChargeId`, changedAt / changedBy, stamps; unique (bookingProfileId, changeNo), index (companyId, changedAt).
  Web: the Bookings row kebab gains Change booking (the same drawer in change mode: the current flight card with Move flight, the roster with existing lines read-only and droppable, new lines addable, contact and remarks; Review change shows the server's preview as the drawer's 'review' view - the summary sentence, from and to, kept / added / dropped chips, the notice band with the charge or the same-day-free note, the waive checkbox and the reason - and the confirm button names the outcome: Move booking, Confirm change, Change and charge 84.00, Change and waive charge) and Change history (a centred viewer of the rows); the listing card shows a "Changed xN" chip.
- `golf.RainCheck` - RAIN CHECKS (user decisions 2026-10-15, approved structure).
