# Golf Management

> Status: IN PROGRESS (Master File Setup being built at `src/modules/golf`).
> Tier: **Product (core system)**.
> Source spec: the 2006 Mission Hills master-file SRS (MH-MasterFile-SRS-V2.1); options are being carried over one by one.

## Purpose
Golf operations: courses, tee-time scheduling and booking, flights/pairings,
handicaps, competitions, pro-shop/scoring as needed.

## Domain model - how a golf course is set up
Golf courses are built from NINE-hole **unit courses** first.
A unit course has a type: `out` (front nine only), `in` (back nine only) or `composite` (either).
A full 18-hole **course** is then formed by picking two unit courses - the 1st as the OUT (front) nine and the 2nd as the IN (back) nine - plus optional standby and floodlit fallback nines.
Hole numbering follows the type (OUT -> 1-9, IN -> 10-18).

## Owns (data)
- `golf.UnitCourse` - 9-hole unit course master file (code, type, completion minutes, floodlight + lighting-fee lead time). **Built.**
- `golf.UnitCourseHole` - hole rows of a unit course (par 3/4/5, handicap index, remarks); numbering fixed by the type (OUT 1-9, IN 10-18, COMPOSITE 1-18). HCP parity follows the numbering context: holes 1-9 take ODD indexes, holes 10-18 EVEN, so an OUT+IN pairing yields a full 1-18 set. Intra-service FK, cascades with the unit course. **Built.**
- `golf.UnitCourseTeeBox` + `golf.UnitCourseTeeBoxDistance` - tee boxes of a unit course (colour code, number, description, measurement unit meter/yard) with PER-HOLE distances (the scorecard's yardage rows; OUT/IN totals are computed, never stored). Cascade with the unit course. Difficulty ratings (course/slope) deliberately live at the 18-hole Course level (2.2.4), not here. **Built.**
- `golf.Course` - the 18-hole course (spec 2.2.4): code/display sequence/description, first nine (OUT|COMPOSITE), second nine (IN|COMPOSITE, must differ from first), optional alternate nine and night nine (must be a floodlit unit course), cross over time, course photo (GCS URL). Column names match the screen labels (user's vocabulary); the legacy zone column is dropped. **Built.**
- `golf.CourseTeeTimeSet` + `golf.CourseTeeTimeSlot` - per-COURSE tee-off/flight time setups (spec 2.2.5/2.2.6 collapsed: flight time is a property of the course - walking courses take longer intervals, unlit courses a shorter day). Versioned by day scope (all/weekday/weekend - public holidays count as weekend by business rule; classification from Company Weekend Days + Public Holidays, no Date Type master) + effective date (seasonal daylight). Slots generated from the header, individually adjustable, front-desk-only flag per slot. **Built.**
- `golf.TransactionType` - the golf billing-item catalog, mirroring membership's Transaction Type: code (unique per company) + charge type (fixed vocabulary: `green-fee` / `caddy-fee` / `buggy-fee` / `no-show` / `miscellaneous` / `package`) + description + THE tax scheme by code via the tax seam (single source - consuming rows such as green-fee matrices and no-show penalties inherit it, never store their own) + `allowPriceOverride` (default OFF - whether the cashier may amend the pre-set price manually when billing; OFF means the resolved rate is binding) + `iconUrl` (public GCS URL of the billing-item icon shown on the catalog and the front-desk billing tiles; uploaded via `POST /transaction-types/icon`, per-env `ASSETS_BUCKET`).
  Sequelize model name is `GolfTransactionType` (membership already registered `TransactionType` in the global model registry); the table is still `golf."TransactionType"`. **Built.**
- `golf.TransactionTypeRate` - the pricing of a transaction type: effective-dated price cards (unique per (type, effectiveDate); resolution = the ACTIVE card with the latest effective date on-or-before the play date, same rule as tee-time sets).
  Matrix charge types (`green-fee`/`caddy-fee`/`buggy-fee`) carry the eight member/visitor × 9/18-holes × weekday/weekend cells; flat charge types (`no-show`/`miscellaneous`/`package`) carry a single `flatAmount` (user decisions 2026-08-06 / 2026-08-27).
  "Weekend" INCLUDES public holidays (platform business rule via `platform/calendarGateway.js` - no third holiday tier); amounts are tax-exclusive (tax comes from the parent's scheme at billing).
  Future-dated cards may be hard-deleted; a card already in force is history (disable instead). Intra-service FK, cascades with the transaction type. **Built.**
  BILLING RULES for the future registration/flight screen (recorded 2026-08-06, binding when built): the green fee is charged AUTOMATICALLY at registration for every player EXCEPT a member whose Membership Type has `isGolfAllow` - so a valid member without golfing rights IS charged the green fee, at the MEMBER price; guests/visitors pay the visitor price. Caddy/buggy fees price by the same member/visitor split. Manual amendment of a resolved price at billing is allowed only when the transaction type's `allowPriceOverride` is on.
- `golf.TransactionTypeElement` - the element lines of a PACKAGE transaction type (chargeType `package`, user decisions 2026-08-27), e.g. Weekday Twin Package 200.00 = 1 × share buggy (100.00) + 2 × caddy (50.00 each).
  Each line: `transactionTypeId` (the owning PACKAGE - parent column named to match `TransactionTypeRate`, user decision 2026-08-27; table renamed from the short-lived `TransactionTypePackageItem` via a guarded boot migration in app.js) + `elementTransactionTypeId` (a peer transaction type of the SAME company - never a package itself, no nesting; an element in use cannot become a package) + `quantity` (1-99) + `unitAmount` (the per-unit allocation of the package price - the revenue breakdown at billing) + `sortOrder`; unique (package, element).
  The package's own SELLING price stays in its flat `TransactionTypeRate` cards; the element sum is shown against it in the editor but deliberately NOT enforced.
  The package header additionally carries `autoTransactionTypeId` (required for packages; same-company, active, non-package - e.g. PAK1 -> GF1): the transaction type that receives the AUTOMATIC balance line at billing.
  Lines are replaced atomically inside the create/update transaction (`packageItems` in the POST/PUT payload); saving a package as a plain charge type clears its lines. Intra-service FK, cascades with the package. **Built.**
  PACKAGE BILLING RULES (user spec 2026-08-28, binding for the future Bill Item stage; supersedes the earlier per-element-tax decision):
  1. Selecting a package inserts DETAIL lines, not one line (analysis requirement): one line per element (quantity × the unit price stored on the element line, billed as-is) PLUS one automatic line to `autoTransactionTypeId` for the balance = package price − Σ(element lines). Example: PAK1 450.00 = BG1 1×101.00 + CD1 2×34.00 + GF1 auto 281.00.
  2. TAX: the PACKAGE's own tax scheme applies to EVERY generated line (the elements' schemes are ignored for package billing); the package Tax Scheme field is back on the setup form.
  3. ROUNDING: line taxes are computed per line, then the LAST generated line's tax is adjusted so Σ(line tax) equals the tax computed directly on the package amount (e.g. 5.72 + 3.85 + 15.91 = 25.48 -> adjust to force the direct 450.00 → 25.47).
- `golf.CourseClosurePlan` + `golf.CourseClosureDay` - Course Closure Plan (spec 2.2.8): the rule header (description/reason, dayScope all|weekday|weekend, nineScope first-nine|second-nine|all, date period capped at one year, daily closure window - both times NULL = whole day) and its GENERATED per-day rows (unique (plan, date); per-day times/nine scope adjustable, isActive false = except a single day). Generation classifies each date server-side through `platform/calendarGateway.js` (Company Weekend Days + Public Holidays; HOLIDAYS COUNT AS WEEKEND) and returns a preview; the PUT saves the reviewed list atomically. Tee-sheet generation (2.2.10/11) will skip/block slots overlapping an active closure day for the affected nines. **Built.**
- `golf.GolfSetting` + `golf.AdvanceBookingOverride` - Golf Specification (per-company settings SINGLETON, pattern of membership.MembershipSetting / ar.Setting; user decisions 2026-09-17), maintained at `/golf/settings`.
  Today: the ADVANCE-BOOKING WINDOW - `advanceBookingDays` (0-365, general rule for everyone) + `advanceBookingHours` (0-23, early opening BEFORE midnight, club-wide, never overridable) + `allowMembershipTypeOverride`.
  Override lines (`membershipTypeId` value ref via membershipGateway, unique per company + type; PUT-replaced atomically; stored even while the flag is OFF, EFFECTIVE only while ON) grant privileged types an earlier window - most clubs use one number, so lines exist only where granted.
  BINDING WINDOW RULE for the booking stage: the window for play date D opens at 00:00 of (D - effectiveDays) MINUS advanceBookingHours, club-local time - e.g. 7 days / 2 hours means at 22:00 members already book the date that would otherwise open at the coming midnight. effectiveDays = the member type's override else the general days; public golfers always general.
  `allowBookingMerge` (club-wide, default OFF; user decisions 2026-09-19) - the MERGE BOOKING rule for the booking stage.
  OFF = exclusive flights: the first confirmed booking claims the WHOLE flight regardless of player count; more players can only be added into that same booking (up to the slot's max players), never as a second booking.
  ON = shared flights: bookings attach to a flight until the slot's max players is reached (a 2-player booking leaves 2 seats open to another booking).
  The rule is read at booking time - flipping it never touches existing bookings. For an 18-hole booking it applies to BOTH occupied cells (start slot + crossover slot).
  `allowSameDayBooking` (default OFF; user decision 2026-09-21) - when OFF the booking window STARTS TOMORROW (club-local): today's flights are not bookable at all - golfers take today's flights by front-desk REGISTRATION (registration stage). ON = the window starts today. Lands in bookingWindow's dateFrom, so the Date picker minimum, search, lock and save all inherit it. Corner case: advance days 0 + same-day OFF = an empty window, a deliberate config outcome.
  `oneBookingPerDay` (default ON; user decisions 2026-09-20) - a member may only be in ONE active booking per play date. COUNTED: bookings they made (bookerGolferId) and bookings where they appear as a 'member' player line; a member-as-guest line is NOT counted; cancelled bookings free the day. Checked at SEARCH (the prompt names the booked flight: "08:05 (WEST, B260900001)") and re-checked at save under the advisory lock for the booker AND every member player line keyed.
  MINIMUM PLAYERS (spec 2.2.12; user decisions 2026-09-19) - two layers so simple clubs stay simple.
  Layer 1: `minPlayersWeekday` + `minPlayersWeekend` on GolfSetting (1-10, default 1 = no restriction; weekend includes public holidays).
  Layer 2: sparse `golf.MinPlayerRule` exception rows - `courseId` (NULL = every course, value ref), `dayScope` all|weekday|weekend, optional `startTime`/`endTime` band (both-or-neither, NULL = whole day, tee time matched in [start, end)), `minPlayers` 1-10; PUT-replaced with the Specification save.
  RESOLUTION at booking for (course, date, tee time): most specific matching rule wins - specific course > every course, time band > whole day, exact dayScope > all; no match falls back to the GolfSetting numbers.
  Save-time validation: rows with identical (course, dayScope) may not overlap in time (at most one whole-day row per key, bands must not intersect); cross-specificity overlaps are legal because resolution disambiguates.
  BINDING ENFORCEMENT RULE: a booking is accepted when its OWN player count meets the minimum OR joining an existing flight brings the flight's TOTAL to the minimum (with merge OFF this degenerates to plain per-booking enforcement).
  GUEST CONTROL (user decisions 2026-09-20) - same two-layer shape, behind a MASTER SWITCH `guestControlEnabled` (default OFF = no restriction anywhere).
  TWO switches per scope, matching the pricing matrix's member vs guest split: allow GUEST (visitor) and allow MEMBER AS GUEST (a member playing under another member's booking); allow/deny only - per-player-type quotas belong to the later player-type rights stage.
  Layer 1: `allowGuestWeekday` / `allowMemberGuestWeekday` / `allowGuestWeekend` / `allowMemberGuestWeekend` on GolfSetting (all default true).
  Layer 2: sparse `golf.GuestControlRule` exception rows - same scoping columns as MinPlayerRule (`courseId` NULL = every course, `dayScope`, optional time band) + `allowGuest` + `allowMemberGuest`; same resolution (most specific wins, fallback to the Layer-1 flags) and the same save-time overlap validation.
  Rules are STORED even while the master switch is OFF, EFFECTIVE only while ON (the membership-override staging pattern). Enforced at booking, re-checked at registration. **Built.**
- `golf.Golfer` + `golf.OtherGolfer` - the PLAYER IDENTITY pair (user decisions 2026-09-17), mirroring AR's Debtor/OtherDebtor split.
  `Golfer` is the THIN identity row every downstream row references (booking, flight player, registration, bill, rain check reference `golferId` - ONE shape, no member/public branching): `golferType` (`member` | `other`) + polymorphic `sourceId` (member -> membership `Member.id`, other -> `golf.OtherGolfer.id`; unique (company, type, source); plain UUID value refs, no FK) + `name`/`memberNo` search SNAPSHOTS refreshed from the source (the Debtor name-snapshot exception - display only, never authoritative) + golf-owned `handicapIndex` (both kinds; membership holds no handicap) + account-level `remarks` + `isActive`.
  `OtherGolfer` is golf's OWN profile master for public / walk-in players (clubs open to the public must never store these people in the membership service): name (single field - counter entry speed), identityNo, gender, birthDate, nationalityCode, mobile, email; platform person vocabulary.
  RULES: member Golfer rows are find-or-created LAZILY at first booking (like Debtor provisioning); public bookings dedupe OtherGolfer by identityNo/mobile FIRST so returning visitors keep one profile (rain checks are liabilities owed to a PERSON - they need durable identity); a public golfer who joins the club is RE-POINTED ('other' -> 'member') keeping the same golferId so history survives; member status / golfing right / credit are NEVER stored in golf - asked LIVE via `platform/membershipGateway.js` (standing + `isGolfAllow`, checked at booking AND re-checked at registration) and `platform/arGateway.js` (`authorizeCharge` advisory at tender pick, `postCharge({ enforceCredit: true })` as the race-proof authoritative gate for charge-to-account settlement). **Tables built; screens/flows arrive with the booking stage.**
- `golf.PaymentType` - Payment Type master file (user decision 2026-09-14): the settlement-tender catalog the front desk picks from when a bill is paid.
  Code (unique per company) + `paymentClass` (fixed vocabulary: `debtor` / `cash` / `member` / `voucher` / `staff` / `online` / `suspend` / `creditcard`) + description + `iconUrl` (settlement-tile icon, same upload flow as the transaction-type icon).
  The future billing/settlement flow branches on the class (debtor -> AR account, member -> member account, suspend -> parked, the rest are tender kinds). Enable/disable via `isActive`, no hard delete. **Built.**
- `golf.NumberingScheme` - Golf-owned document numbering (user decision 2026-09-14): the four `golf-*` series `golf-booking` (Booking No.) / `golf-registration` (Registration No.) / `golf-bill` (Bill No.) / `golf-raincheck` (Rain Check No.).
  The exact shared table shape from `platform/numberingSchemeDef.js` (same as membership/AR - gapless counter lives beside the documents it will number); maintained at `/golf/numbering` via the shared screen component + `platform/numberingController.js` factory; issuance for the future booking/registration/billing/rain-check flows goes through `platform/numberingGateway.js` (`golf-` prefix routes here). **Built.**
- `golf.Booking` + `golf.BookingPlayer` + `golf.FlightLock` - the BOOKING STAGE on the DYNAMIC tee sheet (user decisions 2026-09-19/20, modeled on the 2006 SRS make-booking screens). **Built.**
  BINDING ARCHITECTURE: NO materialized per-day slot table (no TeeSheetSlot) - a day's flight grid is COMPUTED at read time (`bookingAvailability.service.js`) from the resolved CourseTeeTimeSet (exact day scope preferred over 'all', latest effectiveDate <= date; day type via calendarGateway, holidays = weekend) minus active closure days, overlaid with occupancy and unexpired locks. 2.2.10's generate step disappears entirely.
  Per-NINE granularity: bookings start on the FIRST nine (search flow picks course + time); an 18-hole booking also occupies a SECOND-nine crossover cell - the first grid slot at/after start + course.crossOverMinutes - SNAPSHOTTED onto the header (crossNine/crossTime) so later config changes never move existing flights. A flight is identified by NATURAL KEY (courseId, playDate, nine, teeTime); 9-hole play is refused while the set's mustPlay18Until covers the tee time.
  FLOW (the 2006 wizard): (1) Member No FIRST - membershipGateway.getGolfMemberStanding (case-insensitive memberNo; status actionControl allow/warning/barred gates booking; isGolfAllow display-only - non-golfing members book and pay member rate) -> the Date field is limited to the member's window and Course offers all active courses or one; (2) availability returns the 5 NEAREST flights (+/-) around the requested time per course; (3) clicking a flight INSERTS a FlightLock (WHOLE flight incl. crossover cell; one row per cell, unique (company, course, date, nine, teeTime); expiresAt = now + GolfSetting.bookingLockMinutes, default 5, maintained in Golf Specification's Booking Rules) and the player screen shows a live countdown; (4) player lines are Member / Member-as-Guest (member no) or Guest (NAME-ONLY allowed, even 'Guest' - the durable OtherGolfer profile is created/matched at registration; golferId stays NULL until then).
  DOUBLE-BOOKING PREVENTION: every lock/save transaction takes a Postgres advisory lock on (company, course, playDate) - pg_advisory_xact_lock - sweeps expired locks, then re-validates EVERYTHING server-side: window, grid existence, closure, capacity under the merge rule, minimum players (own count OR flight total), guest control (visitor + member-guest switches), lock ownership/expiry. Only then Booking No issues from the golf-booking series (gapless - counter rides the transaction; manual scheme accepts a keyed number), header + details insert, the lock deletes. The future member portal calls this same path.
  Golfer identities provision lazily at first booking (findOrCreate golferType 'member' + snapshot refresh). Cancel = status 'cancelled' + audit fields (canModifyRecord-guarded), which frees the cells implicitly.
  EMAILS (user decisions 2026-09-21/22): confirm AND cancel queue ONE templated email with EVERY player's address CONCATENATED in To: (so each player sees the rest were informed) - booker + member/member-guest lines resolve email via the membership seam; name-only guests have no address until registration; deduped per address. The body lists the flight's players as an HTML TABLE (# / Player / Member No / Type, injected via {{{playersTable}}}). Templates `golf.booking.confirmed` / `golf.booking.cancelled` (tenant-overridable, seeded from the notification catalog; per-company SMTP + branding as usual; v1->v2 rows refreshed by a marker-guarded one-time boot fix in app.js since the seeder is insert-only). Queued through the transactional outbox INSIDE the booking/cancel transaction; enqueue failures are logged, never abort the business write.
  Web: /golf/bookings (GolfBookingsComponent) - day listing (date filter, players subline, status chip, kebab Cancel with centred confirm) + FAB 'New booking' opening ONE drawer dialog with three @switch views (search -> flights -> players+countdown), footer buttons switching per view.
